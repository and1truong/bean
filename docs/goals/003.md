# Goal: Bean v0.3 Administration Console

Bean v0.2 has a semantically correct metadata runtime, but `/admin` is only a generated create form followed by an unlabelled table. This goal turns it into a coherent internal operations console while preserving Bean's View/Action/Policy boundaries.

Bean remains alpha software after this goal. Crash durability, operational qualification, external security review, and signed release engineering remain separate production-readiness work.

## Primary outcome

At completion, an administrator can discover resources, find and inspect records, create or edit them, confirm deletion, manage relations, invoke declared domain Actions, and inspect record history without bypassing compiled metadata.

## Architectural contract

- Add a typed `AdminResource` definition and immutable AppIR representation.
- Generate a useful default AdminResource for each Entity; explicit definitions override its presentation and operations.
- Route all record reads through compiled Views and all writes through compiled Actions.
- Require an authenticated `administrator` for admin metadata, resource, and audit endpoints.
- Validate every configured entity, View, field, relation, and Action reference during compilation.
- Keep Studio definition/release work separate from application-data administration.
- Do not add raw-table mutation endpoints or application-specific core behavior.

## Required capabilities

1. Admin home
   - resource navigation with labels and descriptions
   - release identity and empty/loading/error states
2. Change lists
   - labelled configurable columns
   - exact filters, text search, sorting, and bounded pagination
   - row selection and declared bulk Actions
3. Record workflows
   - separate create and change pages
   - type-appropriate inputs and relation selectors
   - server validation feedback, success state, and delete confirmation
   - readonly system metadata and optimistic version visibility
4. Domain operations and history
   - forms generated from declared Action inputs
   - row and bulk invocation with per-record failure reporting
   - record-scoped audit history
5. Verification and documentation
   - compiler, HTTP, React, and browser acceptance tests
   - definition and architecture documentation
   - `make check` and `make build` pass

## Explicit non-goals

- A public application frontend replacement
- Arbitrary SQL or direct table editing
- Inline editing of unrelated entities
- Import/export, saved views, dashboard charts, or plugin hooks
- User/session/job administration, which needs its own typed system-resource design
- The separate durability and operations roadmap

## Terminal gates

```bash
make check
make build
```
