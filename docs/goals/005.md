# Goal: Bean v0.5 Complete Blog Vertical Slice (completed)

Bean v0.4 proves broad platform mechanics, but its CMS example is still a news fixture rather than a complete usable blog. v0.5 prioritizes one product-shaped application over more platform breadth.

```text
editor saves a draft
→ assigns category and tags
→ publishes
→ visitor reads list/detail/category/tag pages
→ visitor signs up and signs in with a local password
→ member submits a comment
→ editor approves it
→ approved comment becomes public
```

The blog remains metadata under `examples/`; core Go and React packages gain only generic compiled capabilities.

## Primary outcome

A user can run Bean as a complete small blog with posts, categories, tags, local-password signup/login, authenticated comments, comment approval, and draft/publish editorial workflow. The complete browser journey works on SQLite and PostgreSQL and has policy tests proving drafts, pending comments, and privileged Actions do not leak to public or member users.

## Product roles

- **Visitor:** read published posts, categories, tags, and approved comments; sign up and sign in.
- **Member:** visitor capabilities plus submit comments. Self-registration grants only this fixed role.
- **Editor:** create categories/tags, save and edit drafts, publish posts, and moderate comments.
- **Administrator:** editor capabilities plus existing System Admin and Studio access.

Self-registration never grants `editor` or `administrator`; those roles remain administrator-managed.

## Required application behavior

### Blog content

- Posts have title, stable unique slug, excerpt, sanitized rich-text body, author display name, category, tags, status, and publication time.
- Categories and tags have names and stable unique slugs.
- A post belongs to one category and may have many tags.
- Editors create posts as `draft`; the create form cannot choose `published`.
- Publishing is an explicit audited transition and records publication time.
- Public Views always require `published` status. Drafts remain absent from list, detail, category, tag, RSS, search, and direct API reads.

### Local identity

- An application explicitly opts into local registration through compiled metadata.
- Signup accepts display name, normalized email, password, and password confirmation.
- Password policy and hashing remain in the auth module; raw passwords never enter AppIR, audit, logs, Action output, or public manifests.
- A typed registration Action/step creates the user transactionally with a compiler-fixed `member` role. The client cannot submit roles, tenant IDs, or system fields.
- Duplicate email, invalid input, throttling, and retry behavior have stable safe responses.
- A newly registered user can sign in and sign out through the public UI. Login returns to the requested public page instead of always redirecting to Admin.
- Authenticated browser writes, including Webforms, enforce CSRF.

### Comments and moderation

- A signed-in member can submit a comment from a post detail page.
- Post identity is supplied by an immutable route/block binding, not a client-editable hidden field.
- New comments are always `pending`; the client cannot choose status, owner, or author display name.
- Comment ownership and display attribution come from the authenticated request.
- Only editors/administrators can transition `pending` comments to `approved` or `rejected`.
- Only approved comments are public. Pending/rejected comments remain absent from public Views and page/API responses.
- Submission and moderation are audited and preserve Action transaction/idempotency semantics.

### Public blog experience

At minimum, the metadata defines:

- `/` — paginated published post list
- `/posts/:slug` — published post detail, category/tags, approved comments, and member comment form
- `/categories` and `/categories/:slug` — category index and filtered posts
- `/tags` and `/tags/:slug` — tag index and filtered posts
- `/signup` and `/login` — local identity flows
- an RSS route for published posts

Navigation is session-aware: public users do not see Admin/Studio controls; members can sign out; editors/administrators can reach allowed management surfaces.

## Generic platform capabilities required

### 1. Sensitive local-registration Action boundary

- Add a compiler-known password/sensitive input contract and a generic local-user registration Action operation or step.
- Keep default roles literal and compiler-validated against Role definitions.
- Execute user creation and Action audit/idempotency in one declared transaction boundary.
- Return only safe user identity fields.
- Make registration opt-in per application and rate-limit it independently of login.
- Do not expose a raw user-table Action or add application-name branches.

### 2. Route-bound View and Webform blocks

- Pass validated Block bindings into View requests and Webform submissions.
- Distinguish immutable bound values from user-editable form values and reject collisions/tampering.
- Compile-check binding names/types against the referenced View filters or Action inputs.
- Support route context needed by post, category, tag, and comment workflows.
- Preserve the Page → Panel → Block → render-tree architecture.

### 3. Useful generic content rendering

- Add metadata-driven View block presentation for list/detail links, title/body/meta fields, empty states, and cursor pagination.
- Render sanitized rich text as content rather than escaped markup, with adversarial XSS tests.
- Add generic slug validation and a deterministic transaction-time binding for publication timestamps if the existing primitives cannot express them safely.
- Keep presentation configuration generic; no `blog`, `post`, `category`, or `comment` conditionals in core React/Go code.

### 4. Editorial Admin workflow

- Configure AdminResources for posts, categories, tags, and comments.
- Use existing typed relation widgets for category and many-to-many tags.
- Use a dedicated `save_post_draft` create Action and explicit `publish_post` transition.
- Expose approve/reject comment Actions only to editor/administrator policy.
- Show status filters, useful search, relation labels, confirmation, and audit history.

## Architectural invariants

- Definitions → validation → additive migration → immutable AppIR → atomic activation remains unchanged.
- Public and Admin reads execute through Views; all domain and registration writes execute through typed Actions.
- Authorization and route bindings are enforced server-side; hidden UI is not a security boundary.
- Password hashing and session persistence remain in `internal/auth`; password values are never persisted as definition or Action result data.
- Policies fail closed. Administrator bypass remains explicit; editor/member permissions come from metadata.
- SQL and backend-specific behavior remain in DBAL/migration adapters.
- The application is metadata-only under `examples/blog` (the old CMS fixture may redirect to or be replaced by it); core packages remain application-neutral.
- SQLite/PostgreSQL behavior remains contract-equivalent.

## Milestones and evidence

### Milestone 0 — Blog contract and failing baseline

Define the role/policy matrix, content model, route/binding contract, sensitive-input rules, and full browser scenario. Add failing tests for draft leakage, pending-comment leakage, signup role escalation, bound-input tampering, and missing list/detail rendering.

Evidence: contract tests and an acceptance test that fails at the first unsupported step.

### Milestone 1 — Editorial publishing slice

Create the metadata-only blog model and AdminResources. Implement any generic slug/time primitives required to save a draft, assign category/tags, publish it, and read list/detail/category/tag Views.

Evidence: compiler/Action/View tests and browser proof that a draft is hidden until the audited publish transition.

### Milestone 2 — Signup, login, and member session

Implement opt-in local registration through the typed Action boundary, sensitive inputs, public signup/login/logout UI, fixed member role assignment, throttling, and CSRF coverage.

Evidence: auth/HTTP/React tests and a browser-created account that can log in but cannot publish or moderate.

### Milestone 3 — Comment submission and approval

Implement immutable route-bound Webform inputs, pending-by-construction comments, editor approve/reject transitions, and approved-only public rendering.

Evidence: tamper/policy tests and a browser journey from member submission through editor approval.

### Milestone 4 — Public rendering and navigation

Complete metadata-driven list/detail rendering, safe rich text, category/tag navigation, cursor pagination, session-aware navigation, empty/error states, and RSS.

Evidence: React unit tests, XSS tests, and responsive browser acceptance without application-name code branches.

### Milestone 5 — Backend parity and qualification

Run the complete blog journey against SQLite and PostgreSQL, preserve all v0.4 crash/release contracts and reference apps, update docs/capabilities/progress, and cut `0.5.0-alpha`.

Evidence: all terminal gates and archived `docs/goals/005.md`.

## End-to-end acceptance scenario

1. An editor creates a category and two tags.
2. The editor saves a post; status is forced to `draft`.
3. Anonymous list/detail/API/RSS/category/tag requests cannot find the draft.
4. The editor publishes the post; it appears at its slug route and in the correct category/tag lists and RSS.
5. A visitor signs up with display name, email, and password, then signs in.
6. The member submits a comment from the post route while attempting no privileged fields.
7. The comment is pending and invisible publicly.
8. The member is denied publish, moderation, Admin, and role-escalation attempts.
9. An editor approves the comment in Admin with confirmation and audit evidence.
10. The approved comment appears on the post page; a rejected comment never does.
11. Rich text containing malicious script/URL payloads is harmless in stored and rendered output.
12. The same visible outcomes and denials pass on SQLite and PostgreSQL.

## Measurable acceptance criteria

- Self-signup always creates exactly the configured `member` role and no client-controlled privilege fields.
- Passwords are bcrypt-hashed and absent from logs, audit changes, API output, manifests, and persisted idempotency results.
- Every public post query enforces `published`; every public comment query enforces `approved`.
- Draft posts and non-approved comments produce non-leaking not-found/empty behavior on direct requests.
- Saving a new post cannot set `published`; publishing requires the explicit permitted transition.
- Bound post/category/tag values cannot be overridden in Webform or View requests.
- A member can comment but cannot publish, approve/reject, or access Admin/Studio.
- Category and many-to-many tag assignment round-trip through Admin and public filters.
- Rich text XSS fixtures do not execute or produce unsafe URLs.
- The complete browser journey passes against both supported databases.
- Existing definitions/AppIR compatibility, crash safety, and reference applications remain green.

## Explicit non-goals

- Password reset/email verification, OAuth/OIDC/SAML, MFA, invitations, or social login
- User-generated blogs, automatic promotion of members to authors, or multi-site hosting
- Media upload/image processing, newsletters/email delivery, full-text search, or SEO analytics
- Nested comments, reactions, spam scoring, CAPTCHA, or notification delivery
- Arbitrary themes, drag-and-drop page design, custom React/JavaScript, or plugin systems
- Destructive migrations, clustering, HA, or multi-process writers
- Backup/restore and broader operational-readiness work; it follows this product slice

## Terminal gates

```bash
make check

make test-blog
make test-postgres
make build
```

`make test-blog` is the focused deterministic SQLite browser journey. PostgreSQL qualification reuses the same backend-neutral HTTP/browser contract rather than creating a reduced API-only substitute.
