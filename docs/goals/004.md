# Goal: Bean v0.4 Production Platform Vertical Slice (completed)

Bean v0.3 proves that declarative metadata can compile into a useful single-binary application with a coherent administration console. It is still an alpha because its durability guarantees are unqualified, SQLite is its only executable backend, Studio requires raw JSON for semantics, and operators cannot manage runtime state from Admin.

This goal advances every major product plane through one end-to-end workflow:

```text
Visual Studio authoring
→ compile and recoverable publication
→ SQLite or PostgreSQL execution
→ application and system administration
→ crash/restart with preserved invariants
```

The goal is a production-platform foundation, not a claim that every plane is feature-complete.

## Primary outcome

At completion, a technical user can visually author and publish a core Bean application, run the same AppIR against SQLite or PostgreSQL, operate its records and runtime queues from Admin, and recover deterministically from a supported process crash. The complete workflow has automated contract and browser evidence.

## Product position

Bean is a compiled application runtime for developer-built operational web applications. It combines Django Admin-like productivity, compiler-enforced application contracts, and a deployable runtime. It is not a citizen-developer no-code tool or a distributed database platform.

## Architectural invariants

- The compiler and immutable AppIR remain the source of truth.
- Reads execute through Views and writes execute through Actions on every backend and UI surface.
- Admin never becomes a raw-table editor.
- Studio visual editors emit normal typed definitions; they do not create a second metadata format.
- SQL and backend behavior remain behind DBAL and migration adapters.
- Domain writes, audit, outbox intents, jobs, and idempotency records preserve their declared transaction boundary.
- External side effects are never described as exactly-once; retryable delivery is at-least-once.
- Release activation is atomic from the runtime perspective and recovery fails closed on ambiguity.
- SQLite and PostgreSQL observe the same portable error, policy, Action, View, relation, and release contracts.

## Supported failure model

This goal qualifies unexpected Bean process termination and restart on a functioning local filesystem or PostgreSQL service. It does not claim survival from corrupted storage, dishonest fsync implementations, host loss, network partitions, or simultaneous multi-process writers.

## Required capabilities

### 1. Crash-safe runtime

- Document Action, idempotency, release, migration, job, and outbox semantics.
- Persist and validate an input fingerprint with each idempotency key; reject key reuse with a different request.
- Make additive migration application and release activation restart-safe and retryable.
- Validate active-release/AppIR/schema compatibility during startup and fail closed with actionable diagnostics.
- Define persistent job and outbox state machines with claim leases, attempts, retry scheduling, terminal failure, and stale-claim recovery.
- Provide deterministic failure points and a black-box crash/restart harness using the real binary.
- Provide a fast crash gate and a separate repeated qualification target.

### 2. PostgreSQL backend

- Select a backend from an explicit database URL while keeping SQLite file flags compatible.
- Implement parameterized CRUD, predicates, joins, aggregates, transactions, schema inspection, metadata initialization, and additive migrations for PostgreSQL.
- Translate PostgreSQL conflict, unique, foreign-key, serialization, and availability errors into portable DBAL errors.
- Run one reusable DBAL contract suite against SQLite and PostgreSQL.
- Run release, Action, View, relation, policy, and Admin HTTP parity tests against both backends.
- PostgreSQL support in this goal is single-process; pooling, replicas, HA, and online destructive migrations are excluded.

### 3. Production administration

- Add a protected System section distinct from application AdminResources.
- Manage users and roles without exposing password hashes or session secrets.
- Inspect releases, active release identity, migrations, audit entries, jobs, and outbox records.
- Retry or cancel eligible failed jobs/outbox records through explicit system Actions with confirmation and audit.
- Show queue health, attempts, next retry, last error, and stale claims.
- Preserve application-resource search, filters, relation widgets, domain Actions, and history on both backends.

### 4. Typed Studio and visual builder

- Replace JSON-only authoring for the core path with typed visual editors for Entity, View, Action, Policy, and AdminResource.
- Support field/relation editing, View projection/filter/sort configuration, Action operation/input selection, policy role selection, and Admin list/form configuration.
- Keep an advanced JSON editor as an explicit escape hatch for all supported definition kinds.
- Show dependency-aware reference choices, inline compiler diagnostics, migration preview, and release diff before publish.
- Round-trip visual edits through the same definition JSON without losing supported fields.
- Demonstrate a complete visual authoring workflow without typing specification JSON.

### 5. Cross-plane acceptance

The acceptance application must be authored visually and then prove on both backends:

- publish and restart
- Admin create/search/edit/relation/domain Action/delete/history
- policy denial and tenant isolation
- idempotent retry
- scheduled job and outbox intent recovery
- additive release publication
- supported crash/restart recovery

## Explicit non-goals

- Clustering, multi-process writers, replicas, failover, or high availability
- Destructive schema migrations or automated rollback of data transformations
- Exactly-once external effects
- Arbitrary SQL, JavaScript, React, middleware, or plugin escape hatches
- A general drag-and-drop page designer or arbitrary visual programming
- Complete parity with Django Admin or a full database operations console
- Backup/restore, point-in-time recovery, and host-loss recovery; these follow this goal
- Production SLO claims, load envelope claims, or external security certification

## Milestones and evidence

### Milestone 0 — Contract and baseline

- Audit actual disk/database write ordering and current claims.
- Publish the durability, backend portability, Admin system-resource, and visual-definition contracts.
- Add failing tests for each identified semantic gap.

Evidence: architecture notes, capability matrix, and contract tests.

### Milestone 1 — Crash-safe SQLite reference semantics

- Harden idempotency, release/migration recovery, job/outbox state machines, startup validation, and SQLite durability configuration.
- Add targeted process failure points and deterministic restart tests.

Evidence: Action/release/job/outbox contracts and `make test-crash`.

### Milestone 2 — PostgreSQL parity

- Implement the PostgreSQL DBAL/migration adapter and runtime selection.
- Reuse backend-neutral contract suites and execute real PostgreSQL integration tests.

Evidence: SQLite/PostgreSQL parity matrix and integration tests.

### Milestone 3 — System administration

- Add System navigation, safe user management, operational resource lists, queue recovery controls, and audit visibility.

Evidence: HTTP authorization tests, React tests, and browser operator workflow.

### Milestone 4 — Visual Studio

- Add typed editors, reference-aware controls, migration/release preview, and lossless JSON round trips.

Evidence: React round-trip tests and a no-JSON browser authoring workflow.

### Milestone 5 — Product qualification

- Execute the cross-plane application on SQLite and PostgreSQL.
- Run crash/restart scenarios, existing reference apps, compatibility, race, browser, and build gates.
- Document guarantees, deployment configuration, and known limits honestly.

Evidence: all terminal gates and archived goal record.

## Measurable acceptance criteria

- No acknowledged Action mutation is lost in supported crash tests.
- Uncommitted Action state never becomes visible after restart.
- Same idempotency key plus different input is rejected.
- Restart exposes either the previous valid release or the new valid release, never mixed state.
- Interrupted additive publication is safely recoverable or fails closed.
- Committed jobs and outbox intents remain pending, claimed, complete, or terminally failed—never silently lost.
- Stale queue claims are reclaimed; duplicate delivery remains observable and documented.
- SQLite integrity and foreign-key checks pass after crash scenarios.
- The reusable backend contract passes against a real PostgreSQL instance.
- The cross-plane acceptance application produces equivalent visible results on SQLite and PostgreSQL.
- An administrator can inspect and safely recover runtime queue failures without accessing secrets.
- A user can visually author and publish the acceptance application without editing specification JSON.
- Existing definitions and AppIR compatibility remain valid.

## Terminal gates

```bash
make check
make test-crash
make test-postgres
make build
```

`make check` contains deterministic, bounded tests. Longer repeated crash qualification belongs to a separate `make qualify-durability` target and must produce reproducible seeds and retained artifacts on failure.
