# Goal: Build Bean v0.1 End-to-End

You are the primary engineer responsible for designing, implementing, testing, and documenting Bean v0.1.

Do not stop at architecture, scaffolding, pseudocode, TODOs, or partial modules. Continue autonomously until the complete acceptance suite passes.

When requirements are ambiguous but not fundamentally blocking, choose the simplest sound design, record the decision in an ADR, and continue. Do not ask for confirmation for routine engineering decisions.

---

## 1. Product Mission

Build **Bean**, a metadata-driven web application runtime inspired by Drupal’s strongest concepts:

- Entity API
- Field API
- Views
- Webform
- Blocks
- Panels
- Pages
- Users and permissions

A user defines entities, fields, views, forms, blocks, panels, pages, actions, and policies in Bean’s metadata database.

Bean compiles those definitions into a running application providing:

- SQLite-backed typed data storage
- Generated CRUD and domain actions
- REST API
- OpenAPI specification
- Generated administration UI
- Generated public-facing pages
- JSON, CSV, and RSS View renderers
- Authentication and authorization
- Declarative forms
- Declarative page composition
- Seven complete reference applications

The complete server and compiled React frontend must ship as **one executable binary**.

Runtime deployment must require only:

```bash
./bean serve --db ./bean.db
````

Bun is build-time only. No bun process or external frontend server may be required at runtime.

## 2. Fixed Technology Decisions

### Backend

* Go
* Modular monolith
* Standard `net/http` or a small idiomatic router
* SQLite only in v0.1
* A maintained pure-Go SQLite driver; avoid CGO
* Structured JSON logging
* Embedded frontend assets using `go:embed`

### Frontend

* React
* TypeScript
* Vite
* React Router
* TanStack Query for server state
* Zustand for local UI state only
* Playwright for browser E2E tests

Do not store fetched server data or API cache in Zustand.

### Runtime

* One Go binary
* One SQLite database file
* One active Bean application per SQLite database in v0.1
* No required Redis, Postgres, message broker, object store, or cloud service

### API

* REST first
* Generated OpenAPI
* JSON, CSV, and RSS output for Views
* No GraphQL in v0.1

## 4. Core Architectural Invariants

These invariants are mandatory.

### 4.1 Definitions compile into immutable runtime state

Do not interpret metadata from SQLite on every request.

Required lifecycle:

```text
Draft Definitions
      ↓
Validate
      ↓
Dependency Resolution
      ↓
Schema Migration Plan
      ↓
Compile
      ↓
Immutable AppIR
      ↓
Activate Atomically
      ↓
Serve Requests
```

The runtime must use an immutable in-memory `AppIR`.

Publishing a valid release atomically replaces the current `AppIR`.

On restart, Bean loads the active release from SQLite.

### 4.2 Clear semantic primitives

```text
Entity  = what data exists
View    = how data is read
Action  = how data changes
Webform = how user input is collected
Block   = reusable presentation/function unit
Panel   = layout and composition of Blocks
Page    = route, context, access policy, and Panel
Policy  = who may access or mutate data
```

Mandatory rules:

```text
Everything readable is exposed through a View.
Everything writable is executed through an Action.
Every screen is a Page composed from Blocks through a Panel.
Every Webform submits to an Action.
```

Generated CRUD operations are Actions and Views internally. They must not bypass the same validation, policy, transaction, and audit paths used by custom operations.

### 4.3 Native typed tables, not EAV

Application data must use native generated SQLite tables:

```text
article
customer
booking
product
issue
```

Do not store all application records in a generic EAV table or a single JSON blob table.

Metadata definitions may use JSON.

### 4.4 DBAL boundary

No module outside the SQLite adapter and migration implementation may depend directly on SQLite syntax or driver-specific types.

Required layering:

```text
Entity / View / Action
          ↓
Typed Query and Expression AST
          ↓
DBAL
          ↓
SQLite Dialect and Adapter
```

A future Postgres adapter must be implementable without rewriting Entity, View, Action, Webform, Block, Panel, Page, User, or Policy modules.

### 4.5 Generic runtime

The seven reference applications must be definitions and seed data.

Do not implement logic such as:

```go
if entityName == "article" { ... }
if appName == "commerce" { ... }
```

Do not implement equivalent application-specific branches in React.

All domain behavior must be expressed using generic Bean primitives.

## 6. Definition and Release Model

Definitions must be versioned typed objects.

Use a format equivalent to:

```yaml
apiVersion: bean/v1alpha1
kind: Entity
metadata:
  namespace: default
  name: article
spec:
  label: Article
  fields:
    - name: title
      type: string
      required: true
    - name: body
      type: richtext
    - name: status
      type: enum
      options:
        - draft
        - published
```

Required definition kinds:

```text
Entity
View
Action
Webform
Policy
Block
Panel
Page
Role
Menu
Job
```

SQLite metadata must include equivalent tables for:

```text
bean_app
bean_definition
bean_definition_revision
bean_release
bean_release_definition
bean_schema_migration
bean_active_release
```

Each release must contain:

* stable release ID
* application ID
* monotonically increasing version
* definition checksums
* compiled AppIR
* schema migration plan
* OpenAPI document
* creation timestamp
* activation timestamp
* activation status

Compilation must detect:

* invalid references
* missing fields
* relation errors
* cyclic dependencies where forbidden
* duplicate routes
* duplicate machine names
* invalid policies
* incompatible View filters
* invalid Action steps
* invalid Panel regions
* invalid Block inputs
* unsafe schema changes

Diagnostics must include the definition kind, definition name, path, and actionable message.

## 7. Schema Migration Rules

Bean v0.1 must support:

* create entity table
* add field
* add relation
* add index
* add unique constraint
* add composite unique constraint
* create many-to-many join table
* safe metadata-only changes
* safe label and presentation changes

For v0.1:

* Published machine names are immutable.
* Field labels may change.
* Destructive field deletion must be blocked.
* Entity deletion must be blocked when data exists.
* Incompatible type changes must be blocked.
* Automatic data loss is forbidden.
* Unsafe changes must produce clear validation errors.

Do not silently issue `DROP TABLE`, `DROP COLUMN`, or destructive table rebuilds.

Schema changes are applied only during release publication.

A migration failure must leave the previous release active.

## 12. Action Module

```text

assert expression
create record

```

Each Action supports:

* typed input schema
* policy
* validation
* transaction boundary
* preconditions
* mutation steps
* output schema
* audit record
* idempotency key

Examples that must be expressible without custom application code:

* publish an article
* move an issue between states
* place an order while decrementing stock

Example:


## 16. Block, Panel, Page, and Render Modules

### Block

Required Block types:

```text

EntityBlock
WebformBlock
ActionBlock
MenuBlock
```

Blocks must declare typed input requirements.

Example:

```yaml
kind: Block

  name: recent-orders
spec:
  type: view
  inputs:
    customer_id:
      type: uuid
      required: true
  view: recent_orders
```

### Panel

A Panel composes Blocks into layout regions.

Required layouts:

```text
single-column
two-column
sidebar-main
main-sidebar
grid
```

Example:

```text
Panel
├── header
├── sidebar
│   └── Customer EntityBlock
└── main
    ├── Summary ViewBlock
    └── Recent Orders ViewBlock
```

### Page

A Page defines:

* route
* route parameters
* title
* access policy
* context mapping
* Panel
* metadata such as description

Example:

```yaml
kind: Page
metadata:
  name: customer-dashboard
spec:
  route: /customers/:customer_id
  policy: view_customer
  context:
    customer_id:
      source: route.customer_id
  panel: customer-dashboard
```

### Render tree

Backend UI output must use a typed render tree or UI manifest, not arbitrary concatenated HTML.

Example:

```json
{
  "component": "DataTable",
  "props": {
    "title": "Customers"
  },
  "children": []
}
```

React maps registered component names to implementations.

The backend must remain headless-capable.

## 30. Definition of Done

Bean v0.1 is complete only when all statements below are true.

### Build

```bash
make bootstrap
make check
make build
```

pass on a clean checkout.

### Binary

A single generated binary contains:

* Go backend
* SQLite support
* migrations
* frontend assets
* OpenAPI documentation assets
* reference application definitions

No Bun process is needed at runtime.

### Runtime

```bash
./bin/bean demo \
  --app cms \
  --db ./tmp/cms.db \
  --addr 127.0.0.1:8080
```

starts a usable CMS.

The following work:

```text
http://127.0.0.1:8080/
http://127.0.0.1:8080/admin
http://127.0.0.1:8080/studio
http://127.0.0.1:8080/docs
http://127.0.0.1:8080/openapi.json
```

### Tests

All of the following pass:

* Go unit tests
* Go integration tests
* race tests
* frontend lint
* frontend type checking
* frontend unit tests
* frontend build
* Studio Playwright E2E
* CMS Playwright E2E
* CRM Playwright E2E
* Commerce Playwright E2E
* Tracker Playwright E2E
* Booking Playwright E2E
* SaaS Playwright E2E
* Community Playwright E2E
* OpenAPI validation E2E

### Architecture

* No application-specific code exists in core runtime.
* No direct SQLite imports exist outside the SQLite adapter.
* No metadata lookup occurs on the normal request hot path.
* No Webform writes directly to application tables.
* No write bypasses Action authorization and audit.
* No View bypasses policy filtering.
* No frontend route hardcodes a reference application.
* No destructive migration is applied automatically.
* No required implementation remains as a TODO, panic stub, or placeholder.

Finish only after these conditions are satisfied.
