# Goal: Bean v0.2 Semantic Correctness

Bean v0.1 is an executable alpha. Its build and self-authored acceptance tests pass, but it does not yet implement the complete semantics it advertises and must not be described as production-ready.

This goal is the next production-readiness tranche: make Bean's metadata contract truthful, complete the core View/Action/Policy execution model, and prove that accepted definitions cannot be silently ignored or partially executed.

Do not expand into visual polish, new reference applications, external integrations, Postgres, GraphQL, clustering, or marketplace work during this goal.

---

## 1. Primary outcome

At completion:

> Every definition accepted by Bean's compiler has complete, deterministic runtime semantics, or publication fails with an actionable diagnostic.

No supported definition field, Action operation, View feature, policy rule, relation, Webform element, Block input, or Page context mapping may be accepted and then ignored.

Bean remains an alpha after this goal. Production readiness additionally requires later durability, security-review, operational, performance, and release-engineering goals.

---

## 2. Execution contract

Before implementation:

1. Audit the current implementation against `docs/goals/001.md`.
2. Create `docs/capabilities.md` with one row for every advertised feature and one of:
   - complete
   - partial
   - missing
   - unsafe
3. Replace the completed historical milestones in `PLANS.md` with the milestones below.
4. Update `docs/progress.md` as evidence is produced.

During implementation:

- Work milestone by milestone.
- Write a failing contract test before fixing each semantic gap.
- Prefer removing an advertised feature over retaining a partial or ambiguous implementation.
- Reject unsupported metadata at compile time.
- Do not add application-specific conditions to core packages.
- Preserve the immutable AppIR and atomic activation lifecycle.
- Preserve the DBAL boundary and parameterized-query invariant.
- Do not weaken existing concurrency, tenant-isolation, CSRF, or release-safety tests.

Before completion:

```bash
make bootstrap
make check
make build
```

All must pass from a clean checkout.

## 3. Definition contract

Replace unstructured specification decoding with explicit typed source-definition types for every supported kind:

```text
Entity
View
Action
Webform
Policy
Block
Panel
Page
Role
Menu
Job
```

Requirements:

- Unknown specification fields produce diagnostics.
- Required fields are enforced before AppIR creation.
- Defaults are applied in one documented compilation phase.
- Machine names and identifiers are validated consistently.
- References are resolved to typed AppIR identifiers.
- Diagnostics always include kind, name, path, and actionable message.
- Published AppIR contains no `map[string]any` contracts for core semantics.
- Arbitrary JSON remains allowed only where the definition explicitly declares JSON data.
- Definition and AppIR schemas have round-trip and compatibility tests.

The compiler must reject:

- an Action operation or step without an executor
- a View feature without a query-plan representation
- a policy source or operator unsupported by runtime evaluation or DB filtering
- a Webform element unsupported by both server validation and UI rendering
- a Block type or input mapping without a renderer
- a Page context mapping without a typed resolver
- a relation lacking valid cardinality, target, and storage semantics

---

## 4. Action semantics

Implement the complete declared Action operation set:

```text
load record
query records
assert expression
create record
update record
conditional update
delete or soft-delete record
state transition
emit event
schedule job
return result
```

Required model:

- typed Action input and output schemas
- named step results
- typed value bindings from input, context, record, and previous results
- deterministic step ordering
- a single explicit transaction boundary
- policy checks before protected reads and writes
- optimistic concurrency and affected-row checks
- protected state fields writable only through declared transitions
- transactional audit and outbox writes
- idempotency-key persistence and replay behavior
- stable Bean error mapping
- no silent default branch for unknown steps

Required tests:

- every operation in isolation
- multi-entity transaction success
- rollback after failure at each step position
- concurrent conditional updates
- idempotent replay
- owner and tenant denial by known UUID
- audit and outbox atomicity
- protected transition bypass attempts

---

## 5. View semantics

Implement one compiled logical query plan supporting:

```text
selected fields
relationships and joins
filters
contextual filters
exposed filters
sorting
grouping
count, sum, min, max, average
offset pagination
cursor pagination
default and maximum limits
row policies
field redaction
tenant injection
```

Requirements:

- All displays reuse the same compiled query plan.
- Contextual and exposed inputs are typed and validated.
- Cursor tokens are opaque, stable, and reject incompatible View versions.
- Pagination ordering is deterministic.
- Aggregates define null and empty-set behavior.
- Relationship cardinality cannot silently duplicate base rows.
- Policy predicates are composed before query execution.
- Redacted fields cannot leak through sorting, filters, CSV, RSS, errors, or cursor payloads.
- JSON, CSV, RSS, admin, and public rendering observe identical row visibility.
- Unbounded queries remain impossible.

Add reusable DBAL contract tests for joins, grouping, aggregates, and cursor predicates.

---

## 6. Entity, relation, and migration semantics

Complete native-table behavior for:

```text
one-to-one
one-to-many
many-to-one
many-to-many
indexes
unique constraints
composite unique constraints
owner columns
tenant columns
soft deletion
optimistic versions
```

Requirements:

- Relations use declared target fields and database constraints.
- Relation writes execute only through Actions.
- Many-to-many changes are transactional and policy checked.
- Unique and foreign-key failures map to portable Bean errors.
- Migration plans are deterministic and stable across repeated compilation.
- Additive migrations are idempotent or have explicit applied-state checks.
- Invalid, incompatible, or destructive changes fail before any schema mutation.
- Migration SQL is not duplicated across compiler or runtime packages.

Add tests for relation creation, traversal, authorization, deletion constraints, and concurrent unique conflicts.

---

## 7. Policy completeness

Use one explicit policy model at every enforcement boundary:

```text
Route
Page
Panel
Block
View
View row
View field
Action
Webform
Entity relation
```

Requirements:

- Default-deny writes.
- Anonymous, authenticated, role, owner, tenant, field-condition, `and`, `or`, and `not` rules.
- Read and write semantics are distinct.
- Owner/tenant shortcuts compile into the same typed expression/predicate model rather than separate ad hoc paths.
- A policy either compiles fully for its usage site or publication fails.
- Direct lookup and list filtering have equivalent non-leaking behavior.
- Authorization failures never disclose whether another tenant's UUID exists.
- Field redaction applies before every serializer and renderer.

Create a table-driven enforcement matrix covering every boundary and identity type.

---

## 8. Webform and render semantics

For every accepted Webform element, implement matching:

- source-definition validation
- AppIR representation
- server-side validation
- accessible React widget
- error rendering
- Action input mapping

Required behavior includes conditional visibility, conditional required state, repeating groups, multi-step forms, draft client state, and confirmation rendering.

For Blocks, Panels, Pages, Menus, and context mappings:

- validate all typed inputs at publication
- resolve route and context values without global string maps
- enforce policy before child resolution
- fail rendering with a safe typed error when required context is absent
- cover every registered render component with focused tests

---

## 9. Release and compatibility guarantees

Strengthen the definition-to-release path:

```text
Draft
  -> source schema validation
  -> dependency resolution
  -> typed semantic compilation
  -> migration safety validation
  -> immutable AppIR
  -> persistence
  -> atomic activation
```

Requirements:

- Compilation is deterministic for identical inputs.
- AppIR has an explicit format version.
- Old supported AppIR/release fixtures load after upgrades.
- Invalid drafts never alter schema or active release state.
- Migration or release persistence failure never changes active AppIR.
- Restart selects exactly the persisted active release.
- Release checksums cover canonical typed definitions.
- Publication cannot succeed when any feature is only partially compiled.

Add golden fixtures for source definitions, AppIR, migration plans, and OpenAPI.

---

## 10. Test strategy

Add the following gates:

```bash
make test-contract
make test-fuzz-smoke
make test-compatibility
```

`make check` must include them.

Required test classes:

- table-driven unit tests for every operator and definition field
- reusable DBAL contract tests
- compiler/runtime contract pairs
- property tests for expression and policy equivalence
- fuzz tests for definition decoding, expressions, cursor tokens, and HTTP JSON bodies
- integration tests using real SQLite files
- concurrent Action and migration tests
- black-box CLI and HTTP tests against the built binary
- Playwright workflows for the supported UI semantics

Tests must prove negative behavior, including malformed metadata, unsupported operations, privilege escalation, cross-tenant UUID access, stale versions, duplicate idempotency keys, and serializer redaction.

Coverage percentage is not the goal. Every advertised semantic branch must have an executable contract test.

## 11. Required milestones

### Milestone 0: Honest baseline

Deliver:

- `docs/capabilities.md`
- updated `PLANS.md`
- version and documentation identifying Bean as alpha
- failing tests for every currently accepted-but-unimplemented feature

Exit criteria:

- no feature is marked complete without a direct test reference
- unsupported metadata fails closed

### Milestone 1: Typed definitions and AppIR

Deliver typed source definitions, strict decoding, canonicalization, typed reference resolution, AppIR versioning, and golden fixtures.

Exit criteria:

- core semantic contracts contain no untyped maps
- unknown or unsupported fields fail publication

### Milestone 2: Complete Action engine

Deliver all Action operations, bindings, transaction semantics, policy enforcement, idempotency, audit, and outbox guarantees.

Exit criteria:

- every Action operation has success, failure, rollback, and authorization tests

### Milestone 3: Complete View engine

Deliver relationships, joins, filters, grouping, aggregates, offset/cursor pagination, policy injection, and serializer equivalence.

Exit criteria:

- one View contract produces policy-equivalent JSON, CSV, RSS, admin, and public results

### Milestone 4: Relations, policies, Webforms, and render context

Deliver complete relation storage and mutation, the enforcement matrix, supported Webform semantics, and typed Page/Block context resolution.

Exit criteria:

- all declared enforcement boundaries have positive and negative tests
- every accepted element and renderer is executable

### Milestone 5: Release compatibility and semantic hardening

Deliver deterministic compilation, compatibility fixtures, contract/fuzz gates, black-box binary tests, updated documentation, and a clean build.

Exit criteria:

```bash
make bootstrap
make check
make build
```

pass from a clean checkout.

---

## 12. Definition of done

This goal is complete only when:

- `docs/capabilities.md` has no `unsafe` rows.
- Every `partial` or `missing` row is either implemented or explicitly removed from Bean's advertised v0.2 contract.
- The compiler rejects every unsupported semantic construct.
- No accepted Action step is ignored.
- No accepted View feature is omitted from its query plan.
- No policy enforcement boundary bypasses the shared model.
- No Webform or render definition is accepted without a server and UI implementation.
- Contract, fuzz-smoke, compatibility, race, frontend, integration, and Playwright gates pass.
- `make bootstrap`, `make check`, and `make build` pass.
- Documentation calls Bean an alpha and lists remaining production-readiness gates.

Completion of this goal does not authorize a production-ready label. The next goals must cover crash durability and recovery, external security review, operational SLOs and load qualification, and signed release engineering.
