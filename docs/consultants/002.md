## Executive assessment

Bean đã vượt qua giai đoạn “prototype framework”. Nó hiện là một **metadata-driven application runtime có compiler, IR, runtime policy, admin surface và release activation tương đối nghiêm túc**.

Nhưng Bean **chưa nên được định vị là production platform**. Điểm yếu lớn nhất hiện không nằm ở thiếu feature, mà ở **chưa có bằng chứng vận hành khi gặp failure thật**: crash giữa transaction, crash khi publish release, job/outbox bị gián đoạn, WAL recovery, backup/restore, disk full, restart loop, upgrade lỗi, audit/event consistency.

Nói ngắn gọn:

> Bean hiện đã là một nền tảng tốt để tạo và chạy reference applications có kiểm soát.  
> Bean chưa phải là nền tảng đáng tin để người dùng giao dữ liệu thật, workflow thật và trách nhiệm vận hành thật.

Khuyến nghị trọng tâm: **ngừng mở rộng feature surface trong ngắn hạn**. Goal tiếp theo nên là **Durability and Crash Recovery Qualification**.

# 1. Bean đang giải quyết vấn đề gì và nhóm người dùng phù hợp nhất là ai?

## Vấn đề Bean giải quyết

Bean giải quyết vấn đề:

> Làm thế nào để mô tả một ứng dụng dữ liệu/business workflow bằng metadata, rồi để runtime sinh ra database schema, API, admin UI, public pages, policies và actions một cách nhất quán, kiểm tra được trước khi publish.

Điểm khác biệt quan trọng: Bean không phải “database admin UI”. Nó là một **application behavior runtime**.

Các vấn đề cụ thể Bean xử lý tốt:

1. **Giảm chi phí dựng ứng dụng CRUD/workflow có policy**
   - Entity, View, Action, AdminResource, Page, Webform đều được khai báo.
   - Compiler có thể kiểm tra reference, unknown field, type, dependency.

2. **Tránh tình trạng business logic bị phân tán**
   - Read đi qua View.
   - Write đi qua Action.
   - Admin cũng không bypass runtime.
   - Policy, audit, outbox, tenant/owner isolation nằm trong cùng execution model.

3. **Tạo “safe application publishing”**
   - Definitions → AppIR bất biến → migration plan → atomic activation.
   - Đây là một model tốt hơn nhiều so với việc chỉnh database hoặc code live một cách thủ công.

4. **Một single-binary deploy model**
   - Go executable + embedded frontend + SQLite.
   - Phù hợp cho self-hosted, edge/internal deployments, small teams, vertical SaaS nhỏ, departments.

## Nhóm người dùng phù hợp nhất hiện tại

Bean phù hợp nhất với:

### 1. Technical founders / small teams cần internal products nhanh

Ví dụ:

- CRM nội bộ
- lightweight CMS
- issue tracker
- booking system
- admin backoffice
- customer portal đơn giản

Họ chấp nhận YAML/metadata và muốn tránh viết full-stack app từ đầu.

### 2. Agencies / consultants xây ứng dụng nghiệp vụ lặp lại

Bean có thể là runtime để tạo nhiều app theo pattern tương tự:

- data model
- form
- approval flow
- admin console
- public form/page
- audit

### 3. Self-hosted operational apps

Các app chạy trong một tổ chức nhỏ, traffic vừa phải, yêu cầu deploy đơn giản, dữ liệu không quá lớn, chưa cần HA.

### 4. Product teams muốn embedded application platform

Ví dụ một sản phẩm chính muốn cho customer/team cấu hình object, forms, pages, workflows — nhưng chưa muốn xây full low-code engine.

## Nhóm chưa phù hợp

Bean hiện chưa phù hợp với:

1. **Enterprise mission-critical workloads**
   - Chưa có backup/restore verified.
   - Chưa có SLO.
   - Chưa có external security review.
   - Chưa có HA/clustering.

2. **High-scale multi-tenant SaaS**
   - Single process, single SQLite DB, one active app per database.
   - Chưa có load qualification.

3. **Non-technical citizen developers**
   - Studio vẫn chủ yếu là JSON editor.
   - Chưa phải visual builder thật sự.

4. **Teams cần arbitrary custom code/plugin sâu**
   - Bean đang mạnh ở declarative metadata.
   - Nếu mở custom scripting quá sớm sẽ phá compiler guarantees.

# 2. Những phần hiện đã tạo ra giá trị sản phẩm thực tế

Bean đã có nhiều phần tạo giá trị thực, không chỉ là infrastructure.

## 2.1 Compiler + AppIR là giá trị lõi

Đây là tài sản sản phẩm quan trọng nhất.

Bean có:

- strict envelope validation
- unknown-field validation
- typed source definitions
- typed AppIR
- reference validation
- deterministic compilation
- actionable diagnostics
- compatibility tests

Giá trị sản phẩm:

- Người dùng có thể biết app sai trước khi publish.
- Runtime có thể đơn giản hơn vì không cần interpret YAML tùy tiện.
- Có nền tảng cho migration safety, release history, diff, audit, future tooling.

Đây là khác biệt đáng kể so với nhiều low-code/admin builders chỉ lưu JSON config lỏng lẻo.

## 2.2 View/Action separation là thiết kế đúng

Mô hình:

- View cho read
- Action cho write
- Admin cũng đi qua View/Action

là điểm mạnh lớn.

Nó giúp Bean tránh trở thành raw database editor. Nó cũng tạo nền tảng cho:

- policy enforcement
- auditability
- idempotency
- event emission
- job scheduling
- transactional outbox
- future API stability

Đây là một architectural invariant nên giữ chặt.

## 2.3 Generated AdminResource có giá trị ngay

Admin console hiện đã đủ nhiều chức năng để tạo giá trị thật:

- dashboards
- change lists
- search
- filters
- sorting
- pagination
- typed forms
- relation widgets
- delete confirmation
- domain Actions
- bulk Actions
- audit history
- loading/error/empty states

Điểm quan trọng: admin read/write vẫn đi qua View/Action. Đây là khác biệt lớn với Django Admin-style raw model editor.

## 2.4 Single binary + SQLite là một product advantage

Việc đóng gói frontend, runtime và SQLite driver trong một executable Go duy nhất là lợi thế rõ ràng cho:

- trial
- self-hosting
- local/on-prem install
- edge/internal deployment
- CI black-box testing

Không nên vội chuyển sang Postgres/clustering nếu chưa chứng minh được single-node reliability.

## 2.5 Reference applications là bằng chứng tốt

Bảy metadata-only reference applications là tài sản product/devrel tốt:

- CMS
- CRM
- SaaS
- commerce
- booking
- community
- issue tracker

Chúng chứng minh expressiveness ban đầu của platform.

Tuy nhiên chúng chưa chứng minh production readiness. Chúng chứng minh:

> “Bean có thể mô tả nhiều shape ứng dụng.”

Chúng chưa chứng minh:

> “Bean giữ dữ liệu đúng và recover được khi gặp failure.”

# 3. Những tuyên bố hoặc capability có nguy cơ vượt quá mức độ trưởng thành thực tế

Các capability sau có thể đúng về mặt implementation nhưng dễ bị hiểu quá mức.

## 3.1 “Transactional outbox” và “job scheduling”

Nguy cơ overclaim cao.

Có ghi outbox writes và job scheduling, nhưng giới hạn hiện tại nói:

- outbox/job delivery chưa được chứng minh durable trong mọi failure mode
- một process
- chưa crash-recovery qualification đầy đủ

Vậy nên không nên quảng bá như durable background processing platform.

Nên nói chính xác hơn:

> Bean supports transactional recording of outbox/job intents, but delivery/recovery semantics are not yet production-qualified.

## 3.2 “Atomic release activation”

Đây là capability quan trọng nhưng cần chứng minh dưới crash.

Nếu crash xảy ra:

- sau migration nhưng trước activation
- sau activation nhưng trước AppIR load
- giữa schema creation
- khi WAL chưa checkpoint
- khi process restart với partially written metadata

thì hệ thống phải luôn vào một trong hai trạng thái hợp lệ:

- old release active
- new release active

Không được mixed.

Nếu chưa có failure-injection tests, không nên gọi nó production-safe atomic release.

## 3.3 “Tenant isolation” và “owner isolation”

Đây là security-sensitive claim.

Có policy, row predicates, field redaction, non-leaking failures là tốt. Nhưng isolation bug thường nằm ở edge cases:

- joins
- aggregates
- contextual filters
- relation widgets
- admin search
- bulk actions
- export endpoints
- generated CRUD views/actions
- soft deletion
- audit history
- RSS/CSV/JSON renderers

Nếu chưa có adversarial authorization test suite, nên tránh claim mạnh kiểu “secure multi-tenant isolation”.

Nên nói:

> Bean has metadata-level tenant/owner policy enforcement with test coverage, but it has not yet undergone external security review or adversarial isolation qualification.

## 3.4 “Low-code”

Studio hiện chủ yếu là definition editor/JSON editor. Vì vậy “low-code runtime” đúng hơn “visual low-code builder”.

Không nên bán cho citizen developers lúc này.

Nên định vị:

> metadata-driven application platform for technical users

thay vì:

> no-code builder

## 3.5 “Production platform”

Hiện chưa nên dùng cụm này nếu không có qualifier.

Nên nói:

> alpha runtime for metadata-driven applications  
> production-readiness work in progress

hoặc:

> production-shaped architecture, not production-qualified runtime

## 3.6 “Safe migrations”

Chỉ hỗ trợ additive migrations an toàn. Đây là quyết định tốt, nhưng claim phải giới hạn.

Không nên nói “migration system” chung chung như Rails/Django.

Nên nói:

> additive-only migration planner with compiler validation

# 4. Các khoảng trống nghiêm trọng nhất trước khi chạy workload production

Tôi chia thành ba loại: product gap, correctness gap, operational gap.

---

## 4.1 Correctness gaps

Đây là nhóm nghiêm trọng nhất.

### A. Crash recovery chưa được chứng minh

Các câu hỏi cần trả lời bằng test, không phải bằng niềm tin:

- Nếu process bị kill giữa Action nhiều bước thì DB ở trạng thái nào?
- Nếu crash sau domain write nhưng trước audit write thì sao?
- Nếu crash sau audit nhưng trước outbox insert thì sao?
- Nếu crash sau outbox insert nhưng trước response thì client retry có duplicate không?
- Nếu crash khi relation synchronization đang chạy thì relation có partial không?
- Nếu crash khi release activation thì active AppIR/schema có consistent không?
- Nếu crash trong migration thì restart có recover/retry an toàn không?
- Nếu WAL tồn tại sau crash thì startup validation làm gì?

Bean hiện có nhiều capability liên quan trực tiếp tới correctness, nên failure mode phức tạp.

### B. Outbox/job semantics chưa rõ

Cần xác định contract:

- at-most-once?
- at-least-once?
- effectively-once với idempotency?
- job có thể duplicate không?
- event có thể duplicate không?
- event có thể mất không?
- event delivery và domain commit liên hệ thế nào?
- job stuck/in-flight được reclaim thế nào sau restart?

Nếu không có contract rõ, người dùng sẽ tự giả định — và giả định đó thường sai.

### C. Release activation + migration consistency

Vì Bean là metadata-driven runtime, release activation là equivalent của deploy.

Nếu deploy/release có thể tạo trạng thái half-active, toàn bộ platform mất trust.

Cần invariant mạnh:

> Sau bất kỳ crash/restart nào, database phải ở một trạng thái có thể boot được với đúng một active release hợp lệ, và schema phải tương thích với active release đó.

### D. Idempotency cần được chứng minh dưới retry thật

Bean có idempotency keys, nhưng production semantics cần rõ:

- idempotency scope là gì?
- TTL?
- collision behavior?
- same key different payload?
- response replay?
- crash before response but after commit?
- concurrent same-key requests?

Đây là correctness issue, không phải feature polish.

---

## 4.2 Operational gaps

### A. Backup/restore chưa verified

Không thể gọi production nếu không có restore đã kiểm chứng.

Backup không chỉ là file copy. Với SQLite/WAL, cần rõ:

- backup online hay offline?
- dùng SQLite backup API hay checkpoint + copy?
- app quiesce không?
- restore validation gồm gì?
- AppIR/release metadata có restore consistent không?
- restore có chạy integrity check không?
- operator biết RPO/RTO không?

### B. Observability hạn chế

Production cần biết:

- request latency
- Action latency
- View latency
- policy denial counts
- DB busy/lock timeout
- job queue depth
- outbox pending/failed
- release activation failures
- migration duration
- WAL size/checkpoint behavior
- error rate
- panic/restart count

Không cần full enterprise observability ngay, nhưng cần minimum viable ops surface.

### C. No SLO/load qualification

Cần biết Bean chịu được gì trên single process/SQLite:

- concurrent readers/writers
- admin lists with filters/sorts
- relation-heavy forms
- keyset pagination
- aggregate views
- webforms burst
- job dispatcher contention

Không cần optimize sớm, nhưng cần envelope.

### D. Release engineering chưa đủ

Signed/reproducible release pipeline chưa có. Với single binary self-hosted, đây là trust issue.

Cần:

- versioned artifacts
- checksums
- signing
- upgrade notes
- compatibility matrix
- release rollback policy

---

## 4.3 Product gaps

### A. Studio chưa phải visual builder

Đây là product gap thật, nhưng không phải blocker cho early technical users.

Nên hoãn.

### B. Import/export và system-resource administration thiếu

Quan trọng cho adoption, nhưng đứng sau durability/backup/security.

### C. Local auth only

Không phù hợp enterprise. Nhưng với alpha/self-hosted/internal apps, có thể chấp nhận tạm nếu security hardening rõ.

OIDC/SAML nên hoãn đến khi runtime reliability ổn hơn.

# 5. Nên ưu tiên hướng nào tiếp theo?

Đánh giá từng hướng theo impact/risk.

---

## 5.1 Durability và crash recovery

### Impact

Rất cao.

Đây là nền móng để người dùng tin Bean giữ dữ liệu đúng.

Nó trực tiếp bảo vệ:

- Action transactions
- audit
- idempotency
- outbox
- jobs
- relation sync
- release activation
- migrations

### Risk

Trung bình đến cao.

Khó vì cần failure injection, clear semantics, SQLite/WAL understanding, test harness.

Nhưng scope có thể kiểm soát nếu giới hạn vào:

- process crash
- restart recovery
- SQLite integrity
- release/action/job invariants

Không cần giải quyết distributed systems.

### Verdict

Nên làm tiếp theo.

---

## 5.2 Backup/restore

### Impact

Rất cao.

Không có restore thì không có production.

### Risk

Trung bình.

SQLite có backup API tốt, single DB giúp scope nhỏ hơn.

### Vì sao chưa nên đứng trước crash recovery?

Backup chỉ có ý nghĩa nếu runtime có trạng thái consistent để backup/restore. Nếu Action/release/job có thể để DB ở logical state sai sau crash, backup sẽ bảo tồn trạng thái sai đó.

Backup/restore nên là goal ngay sau crash recovery.

---

## 5.3 Security hardening

### Impact

Rất cao.

Đặc biệt vì Bean có policies, tenant isolation, admin endpoints, generated APIs.

### Risk

Cao nếu làm rộng.

External security review nên làm khi runtime semantics ổn hơn. Nhưng một phần security testing nên được thêm song song trong crash goal nếu liên quan đến startup/recovery/admin-only endpoints.

### Verdict

Rất quan trọng, nhưng nên là goal sau durability + backup baseline.

---

## 5.4 Observability và operations

### Impact

Cao.

Production cần visibility.

### Risk

Thấp đến trung bình.

Có thể thêm logs/metrics/health endpoints tương đối nhanh.

### Vì sao chưa đứng đầu?

Observability giúp phát hiện lỗi, nhưng chưa đảm bảo correctness. Nếu crash recovery chưa có contract, metrics chỉ cho biết hệ thống đang hỏng.

Nên làm sau hoặc một phần nhỏ trong crash recovery: startup recovery logs, health check, queue depth.

---

## 5.5 Performance/load qualification

### Impact

Trung bình đến cao.

Cần biết envelope của single-process SQLite.

### Risk

Trung bình.

### Vì sao chưa đứng đầu?

Tối ưu performance trước khi durability rõ có thể che giấu lỗi. Load tests nên đến sau khi biết system recover đúng.

---

## 5.6 Release engineering

### Impact

Cao cho distribution trust.

### Risk

Thấp đến trung bình.

### Vì sao chưa đứng đầu?

Signed/reproducible binary rất cần trước public production release, nhưng không giải quyết data correctness. Nên làm trước beta, sau durability/backup baseline.

---

## 5.7 Developer experience

### Impact

Trung bình.

Better docs, diagnostics, examples, schema autocomplete, CLI improvements đều giúp adoption.

### Risk

Thấp.

### Vì sao chưa đứng đầu?

DX tăng số người dùng trước khi platform an toàn hơn. Với alpha infrastructure, đó có thể là rủi ro.

---

## 5.8 Mở rộng Admin/Studio

### Impact

Trung bình cho demos và adoption.

### Risk

Cao về product distraction.

Bean đã có admin đủ tốt cho alpha. Studio visual builder hấp dẫn nhưng dễ kéo sản phẩm sang no-code UI problem, trong khi reliability chưa xong.

### Verdict

Nên hoãn phần lớn.

# 6. Chọn duy nhất một mục tiêu tiếp theo

## Goal tiếp theo nên là: Durability and Crash Recovery Qualification

### Vì sao goal này phải đứng trước các mục tiêu còn lại

Bean là application runtime. Người dùng sẽ giao cho Bean:

- dữ liệu
- workflows
- audit trail
- admin mutations
- public form submissions
- release metadata
- job/event side effects

Nếu sau crash/restart Bean không có behavior được chứng minh, mọi capability khác đều bị suy yếu.

Backup/restore cần trạng thái consistent. Security review cần biết control flow/recovery semantics. Observability cần biết invariant nào cần quan sát. Performance cần test trên implementation không mất dữ liệu. Release engineering chỉ phân phối binary; nó không làm binary đáng tin hơn về correctness.

### Rủi ro nếu không làm ngay

1. Feature surface tiếp tục mở rộng làm state space crash recovery tăng nhanh.
2. Outbox/jobs có thể trở thành technical debt khó sửa vì user đã phụ thuộc vào semantics mơ hồ.
3. Release activation bug sau này sẽ rất đắt vì liên quan database schema, AppIR và migration history.
4. Admin/Studio mở rộng sẽ tạo nhiều write paths hơn trước khi transactional invariants được khóa.

### Bằng chứng hoàn thành cần có

Không phải “code looks transactional”.

Cần có:

- documented durability contract
- kill-injection test harness
- repeated crash/restart tests
- SQLite integrity checks
- release activation recovery tests
- Action/idempotency/outbox/job recovery tests
- terminal CI gate chạy được
- operator-facing recovery docs

# 7. Đề xuất `GOAL.md`

```md
# GOAL: Durability and Crash Recovery Qualification

## Primary outcome

Bean must have a documented and tested single-node durability contract.

After an unexpected process crash and restart, Bean must always recover to a valid state:

1. The SQLite database passes integrity and foreign-key checks.
2. Exactly one active release is visible to the runtime.
3. The active AppIR and physical schema are mutually compatible.
4. Acknowledged Action commits remain durable.
5. Unacknowledged Actions have well-defined retry/idempotency behavior.
6. Audit, outbox, scheduled job, relation-sync and domain writes remain transactionally consistent.
7. Outbox and job delivery resume according to documented at-least-once semantics.

This goal qualifies process-crash recovery for the current single-process, single-SQLite architecture.

## Scope

### Included

1. Define Bean's durability contract
   - Action commit semantics.
   - Idempotency-key semantics.
   - Audit-write semantics.
   - Transactional outbox semantics.
   - Scheduled job semantics.
   - Release activation semantics.
   - Migration retry/recovery semantics.
   - Startup recovery behavior.

2. SQLite durability configuration review
   - WAL mode.
   - foreign_keys enforcement.
   - busy_timeout.
   - synchronous mode.
   - transaction boundaries.
   - checkpoint behavior.
   - connection lifecycle.

3. Startup recovery checks
   - `PRAGMA integrity_check`.
   - `PRAGMA foreign_key_check`.
   - active release validation.
   - AppIR/schema compatibility validation.
   - pending migration/release-state reconciliation.
   - outbox/job lease recovery.

4. Crash-injection test harness
   - Run Bean as a black-box binary.
   - Execute scripted workloads.
   - Kill the process at randomized and targeted points.
   - Restart.
   - Validate invariants.
   - Repeat for many trials.

5. Targeted failure-injection hooks
   - Before and after Action transaction begin.
   - Before and after domain write.
   - Before and after audit write.
   - Before and after outbox insert.
   - Before and after job insert.
   - Before and after transaction commit.
   - Before response write.
   - During release publish.
   - During migration execution.
   - During active release pointer update.
   - During job dispatch.
   - During outbox dispatch.

6. Recovery qualification for:
   - create Action
   - update Action
   - conditional update
   - delete/soft-delete
   - state transition
   - multi-step transactional Action
   - relation synchronization
   - idempotent Action retry
   - generated CRUD Actions
   - record and bulk Admin Actions
   - Webform submission Action
   - release publish/activation
   - job scheduling and resumption
   - outbox event recording and resumption

7. Operator-facing documentation
   - Durability guarantees.
   - Known non-guarantees.
   - Startup recovery behavior.
   - What to do after crash.
   - How to detect unrecoverable corruption.
   - How this differs from backup/restore.

## Explicit non-goals

1. No Postgres support.
2. No clustering or high availability.
3. No multi-process writer support.
4. No distributed job execution.
5. No exactly-once external side effects.
6. No full backup/restore workflow.
7. No online schema rollback.
8. No destructive or non-additive migrations.
9. No visual Studio expansion.
10. No new Admin feature expansion.
11. No external security audit in this goal.
12. No performance optimization beyond what is required for correctness.
13. No claim of surviving arbitrary filesystem, kernel, hardware or disk-controller lies about fsync.

## Architectural invariants

1. All mutations must go through Actions.
2. Admin mutations must not bypass Actions.
3. Admin reads must not bypass Views.
4. Public reads must not bypass Views.
5. Policy enforcement must remain mandatory for View and Action execution.
6. Domain write, audit write, outbox intent and job intent must be committed atomically when they belong to the same Action.
7. No external side effect may be performed inside the same transaction before the domain commit becomes durable.
8. Outbox/job dispatch must tolerate duplicate delivery attempts.
9. Job and outbox delivery semantics are at-least-once, not exactly-once.
10. Idempotency keys must make client retries safe after ambiguous crashes.
11. Release activation must be atomic from the runtime's perspective.
12. After restart, runtime must load either the previous valid release or the new valid release, never a mixed release.
13. Migrations must be additive and idempotently recoverable.
14. AppIR remains immutable after release creation.
15. Recovery code must be deterministic and testable.
```

# 8. Những phần nên loại bỏ hoặc thu hẹp thay vì tiếp tục mở rộng

## 8.1 Không mở rộng Studio visual builder lúc này

Studio là hấp dẫn về product, nhưng rủi ro kéo Bean vào cuộc chơi no-code UI quá sớm.

Nên giữ Studio ở mức:

- definition editor
- diagnostics
- publish
- release history
- maybe schema-aware editing/autocomplete

Không nên ưu tiên:

- drag-and-drop builder
- visual workflow designer
- theme designer
- marketplace blocks

Lý do: chưa có production trust thì visual builder chỉ giúp nhiều người tạo app chưa đủ an toàn nhanh hơn.

## 8.2 Không mở rộng Admin feature surface thêm nhiều

Admin hiện đã đủ tạo giá trị alpha.

Nên hoãn:

- advanced saved views
- dashboard builder
- inline editing phức tạp
- complex bulk workflows
- spreadsheet mode
- custom layout engine
- admin analytics

Mỗi admin feature mới tạo thêm read/write path cần policy, audit, idempotency, crash tests.

## 8.3 Không mở Postgres/clustering/HA

Không nên thêm Postgres chỉ vì phổ biến.

Single-process SQLite là một product constraint tốt ở giai đoạn này. Nó giúp:

- giảm operational complexity
- test failure mode dễ hơn
- giữ deployment story rõ
- focus vào correctness

Nếu Bean chưa qualified trên SQLite single node, thêm Postgres sẽ nhân đôi state space.

## 8.4 Không mở rộng Jobs thành workflow engine

Hiện Jobs/outbox đã là vùng rủi ro correctness.

Không nên thêm:

- cron DSL phức tạp
- distributed workers
- dependency DAG jobs
- long-running workflow engine
- human approval workflow engine

Trước tiên cần chứng minh at-least-once recovery và stuck job handling.

## 8.5 Không thêm custom scripting/plugin arbitrary

Custom code sẽ phá nhiều compiler guarantee:

- deterministic AppIR
- static validation
- policy predictability
- migration safety
- sandboxing
- reproducibility

Nếu cần extension, sau này nên thiết kế rất cẩn thận với explicit capability model.

## 8.6 Không mở rộng render formats thêm nữa

JSON/CSV/RSS đã đủ. Không nên thêm PDF, email templates, advanced report engine, SSR/SEO pipeline lúc này.

## 8.7 Không hỗ trợ destructive migrations sớm

Additive-only là constraint đúng.

Destructive migration cần:

- backup/restore
- diff UX
- data migration DSL
- rollback semantics
- operator approval
- dry run
- restore drill

Chưa nên làm.

# 9. Roadmap ba giai đoạn

## Phase 1: Production-capable

Mục tiêu: Bean có thể chạy workload thật nhỏ/vừa trên single node với operational contract rõ.

### 1. Durability and crash recovery

Bằng chứng hoàn thành:

- `make check-crash`
- startup recovery validator
- Action/release/job/outbox crash tests
- documented durability contract

### 2. Backup/restore verified

Scope nên gồm:

- online backup using SQLite backup API hoặc documented safe backup mode
- restore command
- restore validation
- integrity check
- foreign key check
- AppIR/schema compatibility check
- release metadata validation
- restore drill test in CI

Acceptance:

- backup từ running instance restore được sang new instance
- restored app pass reference tests
- documented RPO/RTO assumptions
- operator runbook

### 3. Minimal operations surface

Không cần enterprise observability, nhưng cần minimum:

- `/healthz`
- `/readyz`
- startup recovery status
- active release version
- DB status
- job queue depth
- outbox pending/failed
- last backup timestamp if backup system exists
- structured logs
- basic Prometheus metrics hoặc JSON metrics endpoint

### 4. Security baseline hardening

Scope:

- auth/session/CSRF tests
- admin endpoint access tests
- tenant/owner isolation adversarial tests
- generated View/Action authorization tests
- export/render path policy tests
- secure cookie defaults
- password hashing review
- rate limit for login
- audit for admin security events

Không nhất thiết external review ở phase này, nhưng phải có internal threat model.

### 5. Release engineering baseline

Scope:

- versioned release artifacts
- checksums
- signed binaries
- upgrade notes
- reproducible build investigation, nếu chưa full reproducible thì at least documented provenance
- migration compatibility matrix

### Phase 1 exit criteria

Bean có thể nói:

> Production-capable for single-node, self-hosted workloads within documented limits.

Không nên nói enterprise-ready.

Mục tiêu: không chỉ chạy được, mà có bằng chứng đủ mạnh để người khác tin.

### 1. Load qualification

Không nhất thiết optimize ngay. Cần envelope.

Test các workload:

- read-heavy public pages
- admin list filtering/sorting
- relation-heavy forms
- concurrent webform submissions
- bursty Actions
- job/outbox processing
- release activation during traffic
- large-ish datasets per reference app

Output:

- supported dataset sizes
- recommended SQLite pragmas
- max concurrent writers expectation
- latency percentile baseline
- known bottlenecks
- tuning guide

### 2. External security review

Khi durability/backup/security baseline đã ổn, mời review.

Scope review:

- auth/session/CSRF
- policy engine
- tenant isolation
- SQL query construction
- admin endpoints
- release publishing
- definition upload/publish path
- secrets handling
- file path/archive handling if any
- frontend XSS surfaces

### 3. Operational runbooks

Cần docs thực dụng:

- backup/restore drill
- crash recovery
- failed release publish
- stuck jobs
- outbox backlog
- DB locked/busy
- disk full
- upgrade failure
- rollback to previous release if supported
- audit investigation

### 4. Import/export and system resources

Sau khi backup/restore có nền, mới làm import/export application-level.

Scope:

- metadata export
- data export with policy/admin control
- system resource admin
- audit export
- release export/import maybe later

### 5. Upgrade compatibility program

- AppIR compatibility tests mở rộng
- old binary → new binary upgrade tests
- reference apps upgrade matrix
- migration regression suite
- downgrade policy rõ, kể cả “not supported”

### Phase 2 exit criteria

Bean có thể nói:

> Production-confident for documented single-node workloads, with tested recovery, restore drills, security review and operational runbooks.

Mục tiêu: mở rộng adoption và product surface mà không phá invariants.

- Entity designer

Không nên làm full arbitrary visual programming.

Chỉ mở rộng những phần phục vụ production operations hoặc common workflows:

- saved filters

### 4. Optional external auth

Sau security baseline:

- OIDC

### 5. Consider storage/backend expansion only with evidence

Không thêm Postgres vì trend. Chỉ cân nhắc nếu có bằng chứng:

- SQLite write contention là blocker thật
- dataset size vượt envelope

Bean trở thành scalable product, không chỉ scalable infrastructure:

- onboarding tốt hơn
- Studio hữu ích hơn
- operations rõ hơn
- security trust tốt hơn
- extensibility có kiểm soát
- backend expansion nếu có nhu cầu thực

# Final recommendation

**Goal tiếp theo nên là: Durability and Crash Recovery Qualification.**

Lý do: Đây là điểm có tỷ lệ impact/risk tốt nhất vì nó trực tiếp biến Bean từ một runtime alpha giàu capability thành một nền tảng có thể bắt đầu được tin cậy với dữ liệu thật. Nó cũng là điều kiện tiên quyết cho backup/restore, security review, observability, performance qualification và release engineering có ý nghĩa.

Không nên mở rộng Admin/Studio, Postgres, clustering, workflow engine hoặc visual builder trước khi Bean chứng minh được rằng sau crash/restart nó luôn giữ được dữ liệu, release, Action, audit, outbox và job ở trạng thái nhất quán.
