## Kết luận trước

Bean **đã vượt xa một CRUD generator**. Kiến trúc compiler → immutable AppIR → runtime với View/Action làm choke point là nền tảng tốt.

Nhưng feature breadth đang chạy trước maturity.

**Bean v0.3 hiện nên được mô tả là:**

> Một compiled metadata runtime cho developer-built, single-node operational applications.

Chưa nên gọi nó là:

> production application platform / low-code platform / SaaS platform.

Khoảng cách lớn nhất không phải thiếu feature. Nó là **chưa chứng minh rằng state vẫn đúng sau crash**.

### “Transactional outbox” rất dễ gây hiểu lầm

Transaction này:

```text
business write
+
outbox row
```

có thể atomic.

Nhưng:

```text
outbox row
→ external delivery
→ acknowledgement
```

không thể magically exactly-once.

Crash ở đây:

```text
send external event
✓

process crashes

mark delivered
✗
```

=> retry => duplicate.

Bean phải nói rõ:

> committed outbox messages are delivered **at least once**.

Không được ngầm hứa exactly-once.

CMS và issue tracker khá phù hợp.

# 7. `GOAL.md`

Tôi sẽ viết goal đủ chặt để Codex/team có thể thực thi mà ít ambiguity.

# Goal: Crash-Safe Single-Node Runtime

## Primary Outcome

Qualify Bean's single-node runtime so that all committed durable state has explicit, testable crash/restart semantics.

After this goal is complete, an unexpected process termination must not cause:

* loss of committed Action mutations;
* partially visible transactional Action mutations;
* an invalid or unrecoverable active release;
* silent loss of committed outbox records;
* silent loss of committed jobs;
* permanently stuck claimed jobs or outbox records;
* corruption of persisted idempotency state.

Bean must recover automatically after restart whenever the SQLite database itself remains readable and valid.

This goal establishes process-crash durability.

It does not claim high availability, exactly-once external side effects, protection from physical media loss, or disaster recovery.

---

## Supported Failure Model

This goal covers:

* abrupt process termination;
* `SIGKILL`;
* process termination between durable state transitions;
* restart after incomplete release publication;
* restart while jobs are executing;
* restart while outbox deliveries are executing;
* duplicate client retries;
* concurrent use of the same idempotency key;
* SQLite busy/locked failures;
* transaction rollback;
* disk-full/write failure where reproducibly injectable;
* graceful shutdown during active work.

Physical disk destruction, filesystem corruption and host loss are outside this goal and belong to backup/restore qualification.

---

## Required Delivery Semantics

### Actions

A successful Action response means the Action transaction has committed.

After restart:

* all committed mutations remain visible;
* no uncommitted mutation becomes visible;
* audit records and transactional outbox writes committed by the same Action have the same commit boundary.

### Outbox

Once an outbox record commits with its originating transaction, Bean must never silently discard it.

Delivery semantics are:

**at least once**

Duplicate delivery is allowed.

Every outbox message must therefore have a stable immutable event identifier suitable for downstream deduplication.

Bean must not claim exactly-once delivery.

### Jobs

Once a job scheduling operation commits, the job must survive restart until it reaches a durable terminal state.

Job execution semantics are:

**at least once**

A crash after an external side effect but before durable completion may cause the handler to run again.

Every execution must expose a stable job identifier or execution/idempotency token to handlers.

### Releases

The active release pointer must always reference a complete immutable AppIR release.

A crash during publication must leave either:

1. the previous release active; or
2. the new release completely ready and active.

An incomplete release must never become active.

### Migrations

Supported migrations remain additive-only.

Schema changes must preserve compatibility with the currently active release until activation of the new release completes.

A crash after an additive schema change but before release activation must leave the previous release operational.

---

## Scope

### 1. Persisted Runtime State Machines

Document and encode explicit persisted states for:

* releases;
* migration execution;
* jobs;
* outbox records;
* idempotency records.

Transitions must be transactional where required and reject invalid state transitions.

### 2. Restart Reconciliation

Startup must detect recoverable incomplete runtime states.

Examples:

* abandoned job claims;
* abandoned outbox claims;
* staged but inactive releases;
* incomplete publication attempts.

Recovery must be deterministic and idempotent.

### 3. Job Claiming

Implement crash-safe job claiming.

Claims must use durable ownership metadata such as:

* claim token;
* lease or attempt identifier;
* claim timestamp where required.

A process crash must eventually make unfinished work eligible for execution again.

No job may remain permanently invisible because its worker died.

### 4. Outbox Claiming and Delivery

Implement the equivalent crash-safe lifecycle for outbox delivery.

The system must tolerate the crash window:

external delivery succeeds → process crashes → local acknowledgement is not persisted.

The resulting retry and duplicate delivery are expected behavior.

### 5. Idempotency Qualification

Verify behavior for:

* sequential duplicate requests;
* concurrent duplicate requests;
* crash after business transaction commit;
* retry after client timeout;
* reuse of a key with incompatible request input.

Concurrent requests using the same key must not independently execute the same protected Action.

### 6. Release Publication Recovery

Qualification must cover every durable transition between:

definition compilation → migration planning → migration application → release readiness → activation.

Failed or interrupted publication must be inspectable.

An interrupted release may be resumed or abandoned, but must never become accidentally active.

### 7. SQLite Durability Configuration

Production mode must explicitly configure and document durability-critical SQLite settings.

The configuration must not depend on implicit SQLite defaults.

At minimum qualify:

* journal mode;
* synchronous mode;
* foreign keys;
* busy timeout;
* transaction behavior;
* WAL checkpoint behavior.

### 8. Fault Injection Harness

Add deterministic failpoints around critical durable transitions.

Tests must be able to terminate the Bean process at named points and restart the same application database.

The fault harness must exercise the real compiled binary where practical rather than only unit-level mocks.

---

## Explicit Non-Goals

This goal does not include:

* PostgreSQL;
* clustering;
* multi-process writers;
* leader election;
* distributed consensus;
* high availability;
* zero-downtime deployment;
* exactly-once external effects;
* cross-region replication;
* automatic database repair;
* backup scheduling;
* disaster recovery;
* visual Studio improvements;
* new Admin features;
* new definition kinds;
* destructive migrations;
* marketplace or plugin architecture;
* additional authentication providers.

Do not introduce distributed infrastructure to solve single-node correctness problems.

---

## Architectural Invariants

### Invariant 1

All durable business mutations occur through Action transactions.

### Invariant 2

A successful Action cannot depend on asynchronously persisted state that has not yet committed.

### Invariant 3

Audit and transactional outbox records created by an Action share the Action's transaction boundary.

### Invariant 4

The active release is immutable.

Activation changes only the active-release reference; it does not mutate an existing release.

### Invariant 5

An active release must never depend on an incompletely applied schema transition.

### Invariant 6

Additive migrations must remain compatible with the previously active release.

### Invariant 7

Persisted work may execute more than once but must never silently disappear after commit.

### Invariant 8

Worker ownership is temporary.

Worker death cannot permanently own a job or outbox record.

### Invariant 9

Recovery procedures are idempotent.

Running restart reconciliation repeatedly must converge on the same valid state.

### Invariant 10

Database corruption or failed integrity checks must fail closed.

Bean must never silently create a replacement database or continue against known-corrupt state.

---

## Milestone 1 — Specify Durable Semantics

Create a runtime durability specification covering:

* transaction commit boundaries;
* release states;
* job states;
* outbox states;
* idempotency states;
* retry semantics;
* duplicate semantics;
* restart behavior.

Add state-transition tests.

### Completion Evidence

Every persisted state transition has:

* valid predecessor states;
* valid successor states;
* transaction boundary;
* crash behavior;
* retry behavior.

No production runtime behavior relies on undocumented recovery assumptions.

---

## Milestone 2 — Action and Idempotency Crash Qualification

Build a black-box test application containing Actions with:

* multiple database writes;
* audit writes;
* outbox writes;
* optimistic version checks;
* idempotency keys.

Inject termination before and after transaction commit.

### Completion Evidence

After every restart:

* committed records exist;
* uncommitted records do not exist;
* audit/outbox records match the business transaction;
* duplicate idempotent execution cannot occur concurrently.

---

## Milestone 3 — Release and Migration Recovery

Introduce failpoints at every publication boundary.

Test:

* before migration;
* during migration;
* after migration;
* before release-ready state;
* after release-ready state;
* before activation;
* immediately after activation.

### Completion Evidence

After restart:

* exactly one valid release is active;
* active AppIR can be loaded;
* previous release remains runnable where activation did not complete;
* incomplete releases are visible but inactive;
* publication can safely be retried.

---

## Milestone 4 — Crash-Safe Jobs

Implement and qualify durable job state transitions.

Required scenarios include:

* crash before claim commit;
* crash after claim;
* crash during handler execution;
* crash after handler side effect;
* crash before completion commit;
* retryable handler failure;
* permanent handler failure;
* process shutdown with claimed jobs.

### Completion Evidence

No committed job is lost.

No worker death permanently hides a job.

Retries are bounded and observable.

Terminal failure is persisted rather than retried forever.

Duplicate execution is explicitly tested and documented.

---

## Milestone 5 — Crash-Safe Outbox

Apply equivalent qualification to the outbox.

Required scenarios include:

* crash before delivery;
* crash after claim;
* delivery failure;
* successful external delivery followed by crash before acknowledgement;
* restart and redelivery;
* poison message behavior.

### Completion Evidence

All committed events eventually become either:

* durably delivered; or
* durably failed after configured retry policy.

No committed outbox record silently disappears.

Duplicate delivery after the send/ack crash window is demonstrated in tests.

---

## Milestone 6 — SQLite Failure Qualification

Exercise:

* `SQLITE_BUSY`;
* lock contention;
* failed transaction commit;
* disk-full conditions where supported by the test environment;
* WAL growth;
* restart with non-empty WAL;
* clean shutdown;
* abrupt shutdown.

Run SQLite integrity verification after injected failure scenarios.

### Completion Evidence

Expected infrastructure failures return explicit errors and do not violate runtime invariants.

---

## Required Failure Scenarios

The terminal suite must include at least:

1. SIGKILL immediately before Action commit.
2. SIGKILL immediately after Action commit.
3. SIGKILL after audit/outbox writes but before Action commit.
4. Two concurrent requests using the same idempotency key.
5. Client timeout followed by retry using the same key.
6. SIGKILL after migration but before release activation.
7. SIGKILL immediately after release activation.
8. SIGKILL immediately after job claim.
9. SIGKILL during job execution.
10. SIGKILL after external job side effect but before completion.
11. SIGKILL immediately after outbox claim.
12. SIGKILL after external event delivery but before acknowledgement.
13. Retryable job failure.
14. Permanent/poison job failure.
15. SQLite busy/locked failure.
16. Write failure or disk-full condition where injectable.
17. Shutdown while jobs/outbox workers are active.
18. Repeated crash/restart cycles against the same database.

---

## Measurable Acceptance Criteria

### Data Integrity

Across all crash-injection tests:

* zero committed Action mutations are lost;
* zero uncommitted Action mutations become visible;
* zero active releases reference incomplete AppIR;
* zero committed jobs disappear;
* zero committed outbox records disappear.

### Database Integrity

All completed crash scenarios must pass the configured SQLite integrity verification.

### Recovery

The application must restart without manual database modification after every supported process-crash scenario.

### At-Least-Once Proof

Tests must explicitly demonstrate that jobs and outbox deliveries may duplicate in the ambiguous side-effect/acknowledgement crash window.

Documentation must state these semantics.

### Idempotency

Concurrent execution tests must demonstrate that one idempotency key cannot produce multiple successful protected Action executions.

### Repeatability

The crash suite must run repeated fault cycles against the same database, not only fresh databases.

At least 1,000 automated crash/restart cycles must complete without an invariant violation in the qualification job.

### Regression

All existing reference applications and compatibility tests must continue to pass without metadata changes except where semantics were previously ambiguous or incorrect.

---

## Observability Required by This Goal

Only observability necessary to verify durability behavior is in scope.

Expose at minimum:

* pending jobs;
* claimed jobs;
* failed jobs;
* oldest pending job age;
* pending outbox records;
* failed outbox records;
* oldest pending outbox age;
* active release identifier;
* failed/incomplete release count;
* runtime restart/recovery events.

A complete production observability platform is a separate goal.

---

## Terminal Verification Gates

The goal is complete only when all of the following pass:

```text
make lint
make typecheck
make test
make test-integration
make test-contract
make test-appir-compat
make test-race
make test-blackbox
make test-e2e
make test-crash
make test-crash-soak
make build
make check
```

The crash qualification suite must execute the real Bean binary against a persistent SQLite database.

The terminal CI run must include:

* normal test suite;
* deterministic failure-point suite;
* repeated crash/restart soak;
* SQLite integrity verification;
* final restart and functional smoke test using the database that survived the crash soak.

No skipped durability test is permitted in the release qualification job.

---

## Definition of Done

Bean may claim **crash-safe single-node runtime** when:

1. supported crash semantics are documented;
2. those semantics are enforced by persisted state machines;
3. restart recovery is deterministic;
4. all required crash scenarios are automated;
5. repeated crash qualification produces no invariant violation;
6. at-least-once semantics for jobs and outbox are explicit;
7. existing application behavior remains compatible.

Completion of this goal does **not** make Bean production-ready.

It establishes the correctness foundation required for backup/restore, operations, security qualification and load qualification.

Goal này cố tình không đưa backup vào scope. **Backup/restore nên là goal ngay sau nó**, vì đó là failure domain khác: mất database/host thay vì process crash.

# Một điều kiến trúc tôi sẽ đặc biệt bảo vệ

Đừng để Bean tiến hóa thành runtime có escape hatch ở mọi nơi:

```text
custom SQL
custom JS
custom React
custom middleware
custom policy code
```

Càng nhiều escape hatch, compiler càng mất quyền lực.

Bean thú vị chính vì:

```text
metadata
→ compiler knows application
→ compiler can prove things
```

Đó có thể trở thành lợi thế lớn hơn cả Admin UI.

Nếu cần flexibility, extension model sau này nên có **typed contracts rõ ràng**, không phải arbitrary code injection.

---

## Product thesis tôi sẽ dùng cho Bean

> **Bean is a compiled application runtime for building operational web applications from declarative metadata, with application invariants validated before release.**

Ngắn hơn:

> **Django Admin-like productivity, compiler-grade application contracts, one deployable binary.**

Đấy là một product thesis khá sắc. Đừng biến nó thành “build anything”.

**Goal tiếp theo nên là: *Crash-Safe Single-Node Runtime*.** Sau khi goal đó pass bằng fault injection thật, mới chuyển sang **Verified Backup & Restore**.
